# 计划生成能力包 (Plan Generation Skill)

## 概述

本技能包提供训练计划生成所需的基础能力。**5.0 起为提案-确认模式（B5b）**：
计划是持久化实体（`weekly_plans` + `plan_entries`），但 Agent **不再直接落库**
——提案轮算好完整 entries 随 weekly_plan 卡携带（`data.apply` 载荷），用户在
卡上点「确认启用」后，App 直调确定性端点 `POST /api/schedule/weekly-plan/apply`
毫秒级落库。**确认之前，计划绝不进数据库**（根治「计划不知什么时候就出现了」）。

- 用户问「今天练什么」→ 前端直接读确定性 API（`GET /api/schedule/today`，
  纯 DB 读，无 AI 介入）；本技能只服务「给我排一周计划 / 换计划」类请求。
- 训练前零容忍等待：已确认落库的计划不需要 Agent 在场。

## 周/日粒度判断规则（核心决策表，B5b issue #38）

核心模型：**周计划 = 训练框架（结构层），日计划 = 框架内某一天的覆盖（内容层）**。
粒度 = f(原因的影响范围, 框架是否存在)。每次计划请求先过 `get_current_plan`
判定框架，再按下表选择输出粒度——**判定错误的代价高于慢一轮**：

**前置门槛（先于本表，2026-09-28 返工）**：本表只在「计划前置数据已齐」时
生效。`load_history` 后若关键输入（目标 / 经验 / 可用器械 / 每周频次 / 伤病
限制 / 体重）大多未知——典型是**空档案新用户**——先发 **survey_card 调研
问卷**收集缺失项，**不要按保守假设直接排计划**（「档案空就按最保守自重排
一周」是违规错例）；问卷完成后的下一轮再按规则 #1 出整周卡。问卷轮的交付
物就是围栏 ```json survey_card 卡本身（data.questions = [{id, question,
inputType: text|number|select|checkbox, required?, options: [{label, value}]}]），
**纯文本问题清单 = 失败交付**——App 只能从卡片渲染可交互问卷；survey_card
轮不是 weekly_plan 提案轮（不带 data.apply）。

| #   | 条件                                                                                         | 动作                                                                                                                                                                                                                       | apply.scope |
| --- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| 1   | 无周计划（框架不存在）                                                                       | **一律先出整周计划**，哪怕用户说「给我出明天的/下一次的计划」——单日内容依附于框架，框架缺失时日计划无处安放。可在说明里点出「先给你排好整周框架，明天照着周X练」。（前提：档案非空——空档案先走上表前置门槛的 survey_card） | `week`      |
| 2   | 框架在 + 用户明确点名某天 + 原因是**临时的**（雨天改居家一天 / 今天没空换明天 / 出差一天）   | 只改那一天的日计划（覆盖该日条目），其余六天不动                                                                                                                                                                           | `days`      |
| 3   | 框架在 + 原因是**长期框架级的**（退卡没健身房了 / 搬家 / 伤病持续数周 / 器械可用性永久变化） | 整周重算（分化与全部条目按新约束重建）                                                                                                                                                                                     | `week`      |
| 4   | **原因不明**（如「改成居家练」没说为什么）                                                   | **必须先反问**：「这个变化是长期的还是就这几天？」——不许猜、不许默认。用户答复后回到 #2 或 #3                                                                                                                              | —（先问）   |

**规则 #4 判定锚（2026-09-28 GLM 实测返工）**：「临时/长期」的线索必须在**用户原话里显式出现**（今天/明天/这两天/下雨/出差几天 = 临时；退卡/搬家/以后/长期/没健身房了 = 长期）。用户原话无任何时长线索时**禁止出卡**——只回一句反问；在思考里替用户「按长期处理」再出整周卡是典型违规（哪怕猜得像是对的）。
| 5 | 常规「根据我的信息调整一下」（无具体原因点名） | 默认周计划整周更新 | `week` |

判定细则：

- 「临时 / 长期」看**原因的影响范围**，不看用户措辞强度：明天出差一天=临时；
  每周去不了健身房了=长期。判断依据不足时按 #4 反问，宁可多一轮对话。
- #2 的卡仍展示整周（days 数组覆盖 7 天），但 `apply.entries` 只含被调整
  日的条目、`apply.dates` 列出该日——确认后仅替换那一天，其余不动。
- #3 整周重算时必须先读 `get_current_plan`（旧条目里已完成的记录与锚点
  参考价值），再按新约束重建全部条目。
- 无框架但用户只是问「明天练什么」（疑问句而非要计划）→ 直接回答并引导
  建框架（#1），不要凭空报一天动作。

## 能力说明

### 核心能力

1. **周计划提案（提案-确认，5.0）** - 查既有 → 按粒度规则编排 → 卡上携带 apply 载荷 → 用户确认后 App 落库
2. **周/日粒度判断** - 上表五规则（原因影响范围 × 框架存在性）
3. **训练容量科学计算** - 基于 MEV/MRV 的容量分配（知识见 strength-training-designer 技能）
4. **历史数据加载** - 负荷锚点和健身等级
5. **格式验证与修正** - plan 卡格式自检（uiHint 校验回路打回时修订重试）

## 工具列表

| 工具             | 说明                                                                                                                                                      | 参数                                                                                           | 类别 |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---- |
| load_history     | 加载用户历史数据和负荷锚点                                                                                                                                | `include_profile` 等可选                                                                       | 数据 |
| list_exercises   | 按 body_part/equipment/keyword **过滤查询**动作库（分页：默认 30 条/次，返回带 total/has_more）；行含 {id, name, **name_zh**, exercise_type, description} | `body_part`、`equipment`、`keyword`、`limit`、`offset`（建议按目标肌群逐部位查，不做全量拉取） | 数据 |
| get_current_plan | 读本周（或指定周）已持久化的周计划（框架判定第一步）                                                                                                      | `week_id` 可选（缺省=当前周）                                                                  | 数据 |

**注意**:

- `week_id` 缺省时服务器代为推导当前 ISO 周——**不要自己做日历算术**
  （今天是几号、属于哪一周，交给服务器）。
- **没有写计划工具**：`save_weekly_plan` 已随提案-确认架构移除（5.0）。
  落库只发生在用户确认卡片之后，由 App 程序化调用 apply 端点完成。
- 计划确认落库后，今日课表由 `GET /api/schedule/today` 确定性直读——
  用户之后问「今天练什么」，不需要重新生成任何东西。

### apply 载荷形态（weekly_plan 卡 `data.apply`，确认落库的唯一数据面）

```json
{
  "week_id": "2026-W40", // 可缺省（=当前周，服务器推导）
  "scope": "week", // week=整周 upsert / days=单日覆盖
  "split": "push_pull_legs", // scope=week 必填；days 忽略
  "dates": [], // scope=days 必填：被覆盖的日期（YYYY-MM-DD）
  "entries": [
    // PlanEntryInput 形态（与 4.0 的 save 条目同构）
    {
      "entry_date": "2026-09-28",
      "exercise_id": "<list_exercises 真实 id>",
      "target_sets": 4,
      "target_load": { "type": "rpe", "min": 7, "max": 8 },
      "sort_order": 0
    }
  ]
}
```

- `exercise_id` 必须来自 `list_exercises` 返回的真实条目，禁止编造
- `split` 合法值**只有五个**（严格枚举，其余值会被打回）：`full_body` / `upper_lower` /
  `push_pull_legs` / `hybrid` / `custom`
- `target_sets` 正整数；`target_load` 为 `{type: 'rpe'|'percent_1rm', min, max}` 区间
- scope=days 时 `entries` 的日期必须全部落在 `dates` 内（校验回路强制）
- 分化 `split` 按 program-progression 的分化决策表选（每周天数 × 经验等级）；
  决策表已代码化于 `backend/src/services/schedule/progressionPolicy.ts`（真源）
- scope=week 覆盖该周用户的所有训练日（每天一组条目）；休息日不建条目
- **展示与落库同源**：卡上 `days[].exercises[].sets` 的组数/参数必须从同一份
  编排推导（`sets.length` = 该动作 `target_sets`），不得两处数字不一致

### plan 卡（对话展示层）

编排完成后，在回复正文输出 **weekly_plan 卡**（```json 围栏包裹的
uiHint JSON，type: "weekly_plan"，见 knowledge.md §9.3）展示**整周**，
并携带 `data.apply` 载荷（待确认落库）。落库由用户确认触发，不由本技能执行。
单日 / 明日**会话级**计划仍用 plan_card；兼容期 plan_card 亦被校验器接受。

### 动作名中文优先（B5b）

`list_exercises` 返回 `name_zh`（官方中文名，库内 354/354 已回填）。
**面向用户的输出一律用 name_zh**（weekly_plan 卡的 `days[].exercises[].name`、
单日简述 `focus` 文案、正文里的动作名）——中文用户默认中文。
**禁止自行翻译/音译动作名**：`name`（英文）只是库内主键名，不是展示名。
用户以其他语言交流时按用户语言输出，但动作名仍优先取库内对应名。

## 使用方式

### 典型流程（新计划 / 整周重算，scope=week）

```
用户需求 "给我排这周的计划"（或框架级原因要求重算）
  ↓
get_current_plan（先查：本周已有计划？——框架判定）
  ├─ found: true + 常规调整诉求 → 规则 #5，仍整周更新（读旧条目参考）
  └─ found: false（或框架级重算 #3）↓
load_history（画像/锚点/伤病/器械 → 硬约束）
  ↓
list_exercises（两步查询：计划覆盖的每个部位各调一次 body_part 过滤；
  返回页里按器械/伤病过滤；取 name_zh 作展示名；has_more=false 即停）
  ↓
program-progression 技能（分化决策表 + 容量知识 → 一周编排）
  ↓
输出 weekly_plan 卡（整周展示 + data.apply{scope:'week', split, entries}）
+ 一句说明「确认后生效」（不调用任何写工具）
  ↓
（用户点确认 → App 直调 apply 端点落库 → 信息栏即刻可见）
```

### 单日调整流程（scope=days，规则 #2）

```
用户需求 "明天下雨，改成居家练一天"
  ↓
get_current_plan（框架在？→ 在：读出该周条目）
  ↓
load_history（如需）+ list_exercises（按被点名日所需部位 body_part 过滤，
  返回页里再按居家器械过滤）
  ↓
只重排被点名那天的动作 → weekly_plan 卡仍展示整周
（days 覆盖 7 天，未动日子原样）+ data.apply{scope:'days',
dates:[该日], entries:[仅该日条目]}
  ↓
（用户确认 → 仅替换该日条目，其余六天不动）
```

### 原因不明（规则 #4）

「改成居家练」类请求未说明原因时，**先用一句话反问**（不输出卡片）：
「想确认一下：改成居家是长期的安排，还是就这几天（比如下雨）？」
得到答复后再按 #2 / #3 走对应流程。

### 缺勤顺延（Agent 只解释，不执行）

用户错过某个训练日时：

- **绝不重新生成周计划**，也绝不把错过的容量叠加到今天（不补课）
- 顺延/置换由 Service 查表规则确定性处理
  （`backend/src/services/schedule/planAdjustment.ts`）：
  错过的未完成条目 → 今日休息则顺延并入今日；今日已有训练则置换为跳过
- Agent 的职责：向用户解释这条规则、安抚情绪（漏练不是失败），引导
  按下一次训练正常执行；不重排条目、不做容量算术

## 红线（本技能内重申）

- 算术永远留 Service：加重步进、容量合计、日期推导均不在 Agent 侧计算
- 数据访问只经 mcpTools（get_current_plan 即入口）；**写计划没有 Agent 工具**
- `exercise_id` 必须来自 `list_exercises`；`user_id` 由服务器注入，不可伪造
- 计划落库只经用户确认（提案-确认）；任何「先落库再告知」的路径都是违规
